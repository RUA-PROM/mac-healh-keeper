### 6.4 「実際にどのアカウントの権限で push が通ったか」

- git remote は https。HTTPS push は keychain/credential helper 経由のトークンで認証されるはず → ほぼ確実に `adachi-tatsuru` の token (`repo` scope) で push が通った
- commit メタデータ上の `RUA PRUM <info@rua-prum.jp>` は **commit 内部の自己申告**で、push 認証とは無関係。これが「誰が push したか」を log 上で曖昧にしている要因

## 7. 想定原因の分析（仮説と根拠）

### 仮説 A：そもそも保護ルールが未設定 ← **本命**

- 根拠（成立）:
  - §1.1 `/branches/main/protection` → 404 "Branch not protected"
  - §1.2 `protected: false`
  - §1.3 ruleset API 全て `[]`
  - §1.3 `gh ruleset list` 無出力
- 反証: なし
- **判定: 確定**。ユーザの「デフォルトで禁止していたはず」という認識は**事実と一致しない**。GitHub のデフォルトでは新規 repo に保護は付かない（追加設定が必要）。

### 仮説 B：保護はあるが `enforce_admins: false` で admin だけバイパス

- 根拠（成立）: viewer は ADMIN
- 反証（不成立）: そもそも protection オブジェクトが存在しない（§1.1, §1.2）
- **判定: 不成立**。ただし「今後保護を追加するなら enforce_admins=true にしないと、admin である adachi-tatsuru は同じ事ができてしまう」点は要注意。

### 仮説 C：Ruleset の `bypass_actors` にオーナーが入っている

- 根拠（成立）: なし
- 反証（不成立）: ruleset 自体が存在しない（§1.3）
- **判定: 不成立**

### 仮説 D：保護対象が `master` 等別名で `main` は対象外

- 根拠（成立）: なし（default_branch=main、他に保護対象になりそうな classic 設定無し）
- 反証（不成立）: §1.1〜1.3 で main 対象を直接照会済み、いずれも空
- **判定: 不成立**

### 仮説 E：別アカウントで push、または高権限トークン

- 根拠（成立）:
  - `adachi-tatsuru` が ADMIN（§3）
  - token scopes に `repo` あり（§3.1）
  - commit author の email (`info@rua-prum.jp`) が GitHub アカウントに紐付かず author_login=null（§6.3）
- 「別アカウント」というより「**commit author 名義と push 認証主体が乖離**している」状態
- **判定: 部分的に該当（push 主体は adachi-tatsuru 確定。ただし保護が無いので「高権限だから通った」のではなく「誰でも push 権限さえあれば通る」のが実態）**

### 仮説 F：ローカル git hook で阻止されていなかった

- 根拠（成立）: §5.2 通り hook 無し
- 反証: そもそも hook はベストプラクティスに反する押し付け（個人環境依存）であり、GitHub 側保護の代替にはならない
- **判定: 該当するが、根本対策は GitHub 側保護**

### 仮説 G（追加）：CI が「push 前 required status check」になっていない

- 根拠: §4.1 check.yml は `on: push: branches: [main]` で push 後に走る設定
- これは push を止めない設計。required status checks 化するには branch protection か ruleset で「`check` job 通過必須」を明示する必要がある
- **判定: 該当**。CI を「事後通知用」から「事前ゲート」に格上げする運用変更を伴う

## 8. 推奨対応（**実施はしない**・提案のみ）

### 8.1 保護を有効化する 3 通りの選択肢

#### Option 1: Classic Branch Protection を REST API で設定

```bash
# 設定変更を伴うため、本調査では実行しない。ユーザ承認後に別 turn で。
gh api -X PUT repos/RUA-PROM/mac-healh-keeper/branches/main/protection \
  -H "Accept: application/vnd.github+json" \
  --input - <<'JSON'
{
  "required_status_checks": {
    "strict": true,
    "contexts": ["check"]
  },
  "enforce_admins": true,
  "required_pull_request_reviews": {
    "dismiss_stale_reviews": true,
    "require_code_owner_reviews": false,
    "required_approving_review_count": 1,
    "require_last_push_approval": true
  },
  "restrictions": null,
  "required_linear_history": true,
  "allow_force_pushes": false,
  "allow_deletions": false,
  "block_creations": false,
  "required_conversation_resolution": true,
  "lock_branch": false,
  "allow_fork_syncing": true
}
JSON
```

要点:
- `enforce_admins: true` ← **これが無いと admin の adachi-tatsuru は今までと同じ事ができる**
- `required_status_checks.contexts: ["check"]` ← §4.1 の check.yml の job 名と合わせる（実 job 名は GitHub Actions の「Checks」タブで確認）
- `required_pull_request_reviews.required_approving_review_count: 1` ← 1 人体制なら別アカウントで approve するか、外部レビュアーを 1 人加える必要あり
- 1 人運用で approve 必須化が現実的でない場合は `required_pull_request_reviews` を null にして、最低でも `enforce_admins + required_status_checks` だけでも有効化する案も可

#### Option 2: GitHub Ruleset を使う（推奨・新方式）

- GitHub UI: Settings → Rules → Rulesets → New ruleset → Branch ruleset
- target: `main` branch (Include `~DEFAULT_BRANCH` または `main`)
- Enforcement status: **Active**
- Bypass list: **空のまま**（owner を入れないこと。入れると仮説 C 状態になる）
- Rules（最小推奨）:
  - Restrict deletions
  - Block force pushes
  - Require linear history
  - Require a pull request before merging
    - Required approvals: 1
    - Dismiss stale reviews on new commit
    - Require conversation resolution
  - Require status checks to pass
    - Require branches to be up to date
    - check (from check.yml)
  - Require signed commits（任意）

CLI でやる場合は `gh api -X POST repos/.../rulesets` に JSON を投げるが、UI のほうが落とし穴が少ない。

#### Option 3: 最小限「ロック」だけ即時適用（緊急）

- 何も決まらないうちに直 push をとにかく止めたい場合は GitHub UI → Settings → Branches → Add branch protection rule → `main` → `Lock branch` だけ ON で一旦凍結 → 設計後解除する流れも可

### 8.2 既存 push の取り扱い

| 選択 | 内容 | 推奨度 |
| --- | --- | --- |
| そのまま残す | 7dc95d4 / 7c5208b / 808b51d はいずれも docs/issue 化系で、機能コードを破壊していない | **推奨** |
| `git revert` で打ち消し | 3 件分の取り消しコミットを別途作る。履歴は線形のまま残る | 内容に不満があれば |
| `git reset --hard` + force push | **推奨しない**。pull 済みの他開発者・CI tag・既発行 release tag を壊す | 非推奨 |

→ 実害が無い変更なので **revert/reset は不要**。今後の運用ルール固定に注力するのが妥当。

### 8.3 今後のワークフロー提案

```
feature/* ブランチ作成
  ↓ push
PR (base: main, head: feature/*)
  ↓ 自動: check.yml が走る（required status check として強制）
  ↓ レビュー 1 件 approve（Ruleset で必須化）
  ↓ Squash merge（履歴を線形に保つ。Settings で squash 以外を無効化するのが理想）
main 更新
  ↓ 自動: create-release.yaml が release tag を生成
```

追加検討:
- `delete_branch_on_merge: true` に変更してマージ済 feature branch を自動削除
- `allow_merge_commit: false` / `allow_rebase_merge: false` にして squash 強制
- create-release.yaml に「PR merge 由来 commit のみ tag する」ガードを足す（直 push 時にも release が走ってしまう現状の副作用対策）

### 8.4 commit signature 強化（任意）

- `required_signatures: true`（または ruleset の Require signed commits）有効化で、§6.3 のような author_login=null & unsigned commit を弾ける
- ただし全コラボレータが GPG/SSH 署名設定済みである必要があるため、運用上ハードルあり
