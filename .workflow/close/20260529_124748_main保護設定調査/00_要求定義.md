## 0. 経緯

直前の調査（[`memo/20260529_124748_investigation.md`](./memo/20260529_124748_investigation.md)）で、本リポジトリ `RUA-PROM/mac-healh-keeper` の main ブランチに **保護設定が一切無い**ことが判明した。具体的には:

- Classic Branch Protection: **未設定**（API 404）
- Repository Rulesets: **空配列**
- CODEOWNERS: **存在しない**
- viewer (`adachi-tatsuru`) は **ADMIN** 単独運用
- 結果として、直 push が成功しうる状態であり、CI (`make check`) は事後通知でしか機能していない

本件は「そもそも main 保護が無い」状態を **構造的に解消**することを目的とする。

---

## 1. 目的・背景

### 1.1 目的（必須）

main への直 push を全面禁止し、PR + 必須 CI 経由のみで main を更新できる状態を構築する。

### 1.2 背景

- **現状の課題**:
  - main 保護が未設定で、ADMIN 権限を持つ開発者が PR を経由せず直 push できてしまう。
  - `.github/workflows/check.yml` は `on: push: branches: [main]` で push **後**に動くため、CI 失敗時でも push は既に通っている。
  - solo dev 運用のため「自分で書き、自分でレビューする」状態で、構造的な防壁が無い。

- **必要性**:
  - 監査可能な変更履歴（PR 経由のみ）を担保する。
  - CI を事後通知から「事前ゲート」へ格上げする。
  - 緊急時を除き、ADMIN ですらバイパスできない状態を作る。

### 1.3 期待される効果（必須）

- **効果 1**: main への直 push が remote 側で拒否される（実機で `git push origin main` が失敗終了する）。
- **効果 2**: PR の merge には CI (`check`) の成功が必須となる。
- **効果 3**: force push / branch deletion / non-linear merge が拒否される。

---

## 2. 機能要件（概要）

- GitHub Repository Ruleset を `main` に適用（target: `~DEFAULT_BRANCH`）
- enforcement: `active`
- bypass_actors: 空（誰もバイパス不可）
- rules:
  - `pull_request`（PR 経由必須・solo dev のため approving 0）
  - `required_status_checks`（context: `check`）
  - `non_fast_forward`（force push 禁止）
  - `deletion`（main 削除禁止）
  - `required_linear_history`（merge commit 禁止）

詳細は [`02_設計.md`](./02_設計.md) に委譲。

---

## 3. 非機能要件

- **可用性**: solo dev でも自分の PR を自分で merge できること（approving review count = 0）
- **監査性**: 全ての main 変更が PR 経由となり、CI 結果と関連付け可能
- **可逆性**: Ruleset は GitHub UI / API から削除・disable 可能（緊急時の脱出経路）

---

## 4. 制約条件

- public repo、Organization 配下 (`RUA-PROM`)
- 既存 CI ワークフロー（`check.yml` / `create-release.yaml`）は本 issue では変更しない
- 既存の main 履歴は据え置き（revert / reset しない）
- 認可: viewer (`adachi-tatsuru`) は ADMIN なので Ruleset 作成・削除権限あり

---

## 5. 除外要件

- 既存 commit の revert / 履歴書き換え
- CI ワークフロー本体の改修（`check.yml` の job 化、required jobs strategy 等）
- マージ方式の絞り込み（`allow_merge_commit=false` 等の repo 設定変更）
- commit signature 強制（GPG/SSH 署名）
- CODEOWNERS の導入
- `delete_branch_on_merge: true` 化（squash merge 時の `--delete-branch` で対応）

これらは別 issue 候補として §9 残課題で扱う。

---

## 6. 成功基準（受け入れ基準）

以下を **全て**満たした時点で本 issue 完了とする。

1. **Ruleset 適用**: main ブランチに Ruleset が `enforcement: active` で適用されている（`gh api repos/RUA-PROM/mac-healh-keeper/rulesets` で確認可能）。
2. **直 push 拒否**: `git push origin main`（PR merge ではない直接 push）が remote 側で拒否される。
3. **PR 経由必須**: PR 経由でしか main にコミットが入らない（PR rule が active）。
4. **必須 status check**: `check.yml` の context (`check`) が PR の merge gate として強制される。
5. **force push 拒否**: `non_fast_forward` rule が active。
6. **deletion 拒否**: `deletion` rule が active。
7. **linear history**: `required_linear_history` rule が active。

### 6.1 基準（実機検証）— `.agents-project/受け入れ基準ルール.md` §3.2 準拠

> **本 issue は GitHub 側設定変更 + 文書化であり、`./install.sh` / `make install` の実機検証対象外。** 代替として、以下のローカル実機検証エビデンスを `04_review.md` に必ず記録する。
>
> - main にチェックアウトし、空 commit を作って `git push origin main` を実行 → **拒否される**ことを確認（実エラー出力を記録）
> - その後 `git reset --soft HEAD~1` で空 commit を取り消す（reset --hard は禁止）
> - 既存 PR の `gh pr checks` で CI 成功確認 → `gh pr merge --squash --delete-branch` で merge 成功（**`--admin` フラグは使わない**）

本基準の根拠は [`.agents-project/受け入れ基準ルール.md`](../../.agents-project/受け入れ基準ルール.md) §3.2–3.4。

## 7. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| Ruleset の context 名 `check` が実 CI と不一致 | merge gate が機能しない | 既に `gh run list` で `check` 確定。02 設計で明示 |
| `bypass_actors: []` のため緊急修正時に main を直せない | 障害復旧の遅延 | 緊急時は Ruleset を一時 disable (`PATCH .../rulesets/{id}` で enforcement=disabled) する運用に統一。**bypass_actors に ADMIN を入れない** |
| `required_linear_history` で既存 merge ワークフローと衝突 | merge commit が拒否される | 02 設計で squash merge への統一を明文化、PR でも `--squash` 使用 |
| Ruleset 作成 API 呼び出し時の JSON 形式ミス | 設定失敗 | `--input -` で stdin 経由、レスポンスを変数受けして検証 |
