## 1. 概要

### 1.1 システム概要

mtime ベースのみで肥大化を防げないログを、サイズ/行数（または世代）でローテートし、`.out`/`.err` も対象化、全ジョブ共通の終了処理から確実に呼び、cooldown/events を排他制御する。

### 1.2 用語集

| 用語 | 説明 |
| ---- | ---- |
| ローテート | ログを上限で切り詰める/世代退避すること |
| 世代 | `.1`/`.2` 等の退避ファイル |
| ロック | 並行書き込みの排他制御 |

---

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 肥大化の防止

- **As a** 長期稼働する Mac の利用者
- **I want to** 追記ログがサイズ/世代で自動的に切り詰められる
- **So that** ディスクが枯渇しない

**受け入れ基準**:

- `monitor.log`/`events.log` が上限サイズ/行数を超えると切り詰め/退避される。
- mtime に依存せず肥大化が止まる。

#### ストーリー 2: 取りこぼしの防止

- **As a** 開発者
- **I want to** 全ジョブの終了時に必ずローテートが走る
- **So that** 特定ジョブだけログが膨らむ偏在が無くなる

**受け入れ基準**:

- monitor/docker/uptime/refresh の終了時にローテートが呼ばれる。
- `.out`/`.err` も対象に含まれる。

#### ストーリー 3: 安全な並行書き込み

- **As a** 開発者
- **I want to** events と cooldown の更新が排他制御される
- **So that** 並行追記/read-modify-write で破損しない

**受け入れ基準**:

- 同時実行時に cooldown の更新がロックで直列化される。
- ローテーション失敗・ディスク不足が記録される。

### 2.2 BDD ユースケース

#### ユースケース 1: サイズ超過ローテート

ログが上限を超えると切り詰め/退避される。

**シナリオ 1: 上限超過で退避**

```gherkin
Feature: サイズ超過ローテート
  Scenario: monitor.log が上限を超えると世代退避され新規ファイルが小さくなる
    Given monitor.log が上限サイズを超えている
    When rotate_logs を呼ぶ
    Then monitor.log が上限以下に切り詰め/退避され肥大化が止まる
```

**シナリオ 2: 上限未満は据え置き**

```gherkin
Feature: サイズ超過ローテート
  Scenario: 上限未満なら何もしない
    Given monitor.log が上限未満
    When rotate_logs を呼ぶ
    Then ファイルは変更されない
```

#### ユースケース 2: out/err の対象化

`.out`/`.err` もローテーション対象に含む。

**シナリオ 1: err ファイルも退避**

```gherkin
Feature: out/err の対象化
  Scenario: 上限超過の .err が退避される
    Given launchd.monitor.err が上限を超えている
    When rotate_logs を呼ぶ
    Then .err も切り詰め/退避される
```

#### ユースケース 3: 排他制御

cooldown 更新がロックで直列化される。

**シナリオ 1: 並行更新の直列化**

```gherkin
Feature: 排他制御
  Scenario: 2 プロセスが同時に cooldown を更新しても破損しない
    Given 2 つのジョブが同時に should_notify を呼ぶ
    When 双方が cooldown を更新する
    Then ロックにより直列化され記録が壊れない
```

#### ユースケース 4: 失敗の可視化

ローテーション失敗を握り潰さない。

**シナリオ 1: ディスク不足の記録**

```gherkin
Feature: 失敗の可視化
  Scenario: 書き込み失敗時にエラーを記録する
    Given ローテーション先への書き込みが失敗する状況
    When rotate_logs を実行する
    Then エラーが記録され沈黙しない
```

### 2.3 ビジネスルール

- ローテートは原子的（tmp→mv）に行う。
- 上限サイズ/世代数は 1 箇所で設定管理する。
- 既存ログのパス・書式を壊さない。

---

## 3. 非機能要件

### 3.1 パフォーマンス要件

- ローテートはジョブ実行を著しく遅延させない。

### 3.2 セキュリティ要件

- ロック/一時ファイルは固定の安全な場所に作り競合・リンク攻撃を避ける。

### 3.3 ユーザビリティ要件

- ログ閲覧コマンド（`mac-health` 等）が世代ファイルも辿れる。

### 3.4 可用性要件

- ロック取得失敗時もジョブ本体は継続できる（ローテートはベストエフォート + 記録）。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- `rotate_logs`（および共通終了関数）のシグネチャ・対象拡張子を 02 で定義する。

### 4.2 データ形式要件

- ログ書式（`[ts] ...` / `[ts] [level] [job] ...`）を維持する。
