# 要件定義書: サブ B Swift アプリの責務分割

**プロジェクト名**: サブ B Swift アプリの責務分割（God class 解消）
**作成日**: 2026 年 05 月 27 日
**最終更新**: 2026 年 05 月 27 日

> **重要**: **このドキュメントは常に更新**します。
>
> **用語**: [.agents/CONCEPTS.md §用語規約](../../../../.agents/CONCEPTS.md#用語規約) を参照。

## 1. 概要

### 1.1 システム概要

662 行の `AppDelegate` に集中する責務を、メトリクス収集（Domain）・シェル実行（Infra）・メニュー構築（UI）へ分割し、状態変更（command）と状態取得（query）を分離する。振る舞いは不変。

### 1.2 用語集

| 用語 | 説明 |
| ---- | ---- |
| Domain | 業務ロジック（メトリクスの算出・ジョブ状態モデル） |
| Infra | 外部資源アクセス（シェル・launchctl） |
| UI | NSMenu 構築・表示 |
| CQRS | 状態変更（command）と状態取得（query）の分離 |

---

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 層分割による可読性向上

- **As a** 開発者
- **I want to** 収集・実行・表示の責務が別々の型に分かれている
- **So that** 変更箇所を局所化でき AI も理解しやすい

**受け入れ基準**:

- `MetricsCollector`(Domain)・`ShellRunner`(Infra)・`MenuBuilder`(UI) 相当に分割されている。
- `AppDelegate` は各層の調整役（orchestration）に縮小する。

#### ストーリー 2: CQRS によるジョブ操作の分離

- **As a** 開発者
- **I want to** ジョブの ON/OFF（command）と状態取得（query）が分かれている
- **So that** query に副作用が無く挙動が予測できる

**受け入れ基準**:

- `toggleJob` の状態変更処理と `launchctl list` による状態取得が別関数に分離されている。
- query 側に状態変更の副作用が無い。

#### ストーリー 3: メニュー構築の分解

- **As a** 開発者
- **I want to** 巨大な `rebuildMenu` が小さな構築単位に分かれている
- **So that** メニュー項目の追加・変更が容易になる

**受け入れ基準**:

- `rebuildMenu` がセクション単位の小さなメソッド/型に分解されている。

### 2.2 BDD ユースケース

#### ユースケース 1: 振る舞い不変のリファクタ

責務分割の前後でユーザーから見た挙動が変わらない。

**シナリオ 1: メトリクス表示が不変**

```gherkin
Feature: 振る舞い不変のリファクタ
  Scenario: 分割後もメニューの表示項目が同一
    Given 同一のメトリクス入力を与える
    When 分割後の MenuBuilder でメニューを構築する
    Then 分割前と同じ表示項目・順序になる
```

**シナリオ 2: ジョブ状態取得は副作用なし**

```gherkin
Feature: 振る舞い不変のリファクタ
  Scenario: query がジョブ状態を変更しない
    Given あるジョブが loaded である
    When 状態取得 query を 2 回呼ぶ
    Then ジョブの loaded 状態は変化しない
```

#### ユースケース 2: ジョブ ON/OFF コマンド

`toggleJob` 相当の command は状態を切り替え、結果の確認は query で行う。

**シナリオ 1: トグルで状態が反転**

```gherkin
Feature: ジョブ ON/OFF コマンド
  Scenario: command 実行でジョブの loaded が反転する
    Given ジョブが unloaded
    When toggle command を実行する
    Then その後の query でジョブが loaded になる
```

### 2.3 ビジネスルール

- query に状態変更の副作用を書かない（spec/06）。
- 禁止命名（helpers/misc/common/utils）を使わない（spec/03）。
- 分割の判断順は spec/06（可読性 > 単一責務 > 仕様整合 > 変更容易性 > 保守性 > 再利用性 > 実装効率）に従う。

---

## 3. 非機能要件

### 3.1 パフォーマンス要件

- メトリクス更新・メニュー再描画の体感速度を悪化させない。

### 3.2 セキュリティ要件

- シェル実行の注入対策はサブ F に委譲。本サブは Infra への切り出しまで。

### 3.3 ユーザビリティ要件

- メニュー項目・文言・並びは変えない。

### 3.4 可用性要件

- 分割後も `swiftc`/Swift Package でビルドできる。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- 公開される外部 I/F（CLI・launchd ラベル）は変えない。

### 4.2 データ形式要件

- `MetricsSnapshot`/`JobStatus` の意味を維持する（内部リファクタは可）。

---

## 5. 制約事項

- Swift / Cocoa。振る舞い不変のリファクタ。サブ A のテストで挙動を固定して実施する。
