## 1. 概要

### 1.1 システム概要

空の `docs/` に、Mac Health Keeper のアーキテクチャ概要とディレクトリ構成を中心としたシステム仕様書を整備し、実装との整合を保つ。

### 1.2 用語集

| 用語 | 説明 |
| ---- | ---- |
| システム仕様書 | アーキテクチャ・構成・コンポーネント関係を記す技術文書 |
| ジョブ | launchd が起動する監視/再起動スクリプト |

---

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 全体像の把握

- **As a** 新規参画者 / AI エージェント
- **I want to** docs を読めばシステム全体像が分かる
- **So that** 変更箇所の影響範囲を素早く判断できる

**受け入れ基準**:

- アーキテクチャ概要（Swift UI / シェルジョブ / launchd の関係）が図/表である。
- ディレクトリ構成（`src`/`scripts`/`launchagents`/`docs`）が説明される。

#### ストーリー 2: 規約準拠の文書

- **As a** レビュワー
- **I want to** 仕様書が `.agents/DOCS_RULES.md` に従う
- **So that** 一貫した粒度・命名で保守できる

**受け入れ基準**:

- `.agents/DOCS_RULES.md` の想定構成・命名に沿う。
- document_id（UUID）が付与されている。

### 2.2 BDD ユースケース

#### ユースケース 1: システム仕様書の存在確認

docs に仕様書が整備されている。

**シナリオ 1: アーキテクチャ仕様書がある**

```gherkin
Feature: システム仕様書の存在確認
  Scenario: docs にアーキテクチャ仕様書が存在する
    Given 整備後の docs ディレクトリ
    When ディレクトリを確認する
    Then アーキテクチャと構成を記したシステム仕様書が存在する
```

**シナリオ 2: 規約準拠**

```gherkin
Feature: システム仕様書の存在確認
  Scenario: 仕様書が DOCS_RULES の構成に沿う
    Given 作成したシステム仕様書
    When 構成・命名・document_id を確認する
    Then .agents/DOCS_RULES.md の想定に適合する
```

#### ユースケース 2: 実装との整合

仕様書が現行実装を正しく反映する。

**シナリオ 1: ジョブ一覧の整合**

```gherkin
Feature: 実装との整合
  Scenario: 仕様書のジョブ一覧が launchagents と一致する
    Given launchagents の plist テンプレート群
    When 仕様書のジョブ一覧と突き合わせる
    Then monitor/docker/uptime/refresh が漏れなく記載されている
```

### 2.3 ビジネスルール

- 「生きているドキュメント」として各サブ完了時に更新する旨を明記する。
