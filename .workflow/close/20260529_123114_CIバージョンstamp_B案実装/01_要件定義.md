# 要件定義書: CI（GitHub Actions）でバージョン stamp する B 案の実装

**プロジェクト名**: Mac Health Keeper / CI stamp B 案
**作成日**: 2026 年 05 月 29 日
**最終更新**: 2026 年 05 月 29 日

---

## 1. 概要

### 1.1 システム概要

`create-release.yaml` を `macos-latest` 化し、`make build`（Issue B 成果物）で `.app` を組み立て、CFBundleVersion を tag から注入して Release artifact に upload する。

### 1.2 用語集

| 用語 | 説明 |
|------|------|
| Release artifact | GitHub Releases に添付される配布ファイル |
| fetch-depth: 0 | actions/checkout のオプション。git 履歴を全取得（tag 含む） |
| macos-latest | GitHub Actions の macOS runner（plutil 利用可） |
| Gatekeeper | macOS の署名検証機構 |

---

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: エンドユーザーが Release artifact を DL したい

- **As a** Mac Health Keeper のエンドユーザー
- **I want to** GitHub Releases から `.app.zip` を DL して即試したい
- **So that** `git clone` + `./install.sh` の手順を省略したい

**受け入れ基準**:

- Releases ページに `.app.zip` が掲載されている
- 展開後、`Contents/Info.plist::CFBundleVersion` が tag 値と一致

#### ストーリー 2: 開発者が CI artifact で動作確認したい

- **As a** 開発者
- **I want to** PR / tag 付き commit からの artifact を DL してテストしたい
- **So that** 環境差なくバイナリの動作を確認できる

**受け入れ基準**:

- artifact を DL → 展開 → 起動できる（署名なしのため Gatekeeper 警告は許容）

### 2.2 BDD ユースケース

#### UC1: Release artifact の生成

**シナリオ UC1-S1: tag push で artifact が生成される**

```gherkin
Feature: Release artifact 生成
  Scenario: tag push で .app.zip が Releases にアップロードされる
    Given main ブランチで commit が積まれ、tag を打つ条件が揃った
    When create-release.yaml が起動する
    Then `MacHealth-<tag>.app.zip` が Releases に upload される
    And Release notes に CFBundleVersion 値が記載される
```

#### UC2: CFBundleVersion の注入

**シナリオ UC2-S1: artifact の CFBundleVersion が tag と一致**

```gherkin
Feature: CFBundleVersion 注入
  Scenario: 生成された .app の CFBundleVersion が tag 値と一致する
    Given tag `vYYYYMMDD.HHMMSS` または semver tag が存在
    When CI で `.app` を組み立てる
    Then defaults read .../Info CFBundleVersion が tag 値（または git describe 出力）と一致する
```

#### UC3: A 案との一致

**シナリオ UC3-S1: install.sh stamp 結果と CI artifact CFBundleVersion が一致**

```gherkin
Feature: A 案との一致
  Scenario: 同 commit から install と DL artifact が同じ CFBundleVersion を持つ
    Given 同一 commit
    When ローカル ./install.sh と CI artifact 両方で CFBundleVersion を比較
    Then 一致する
```

#### UC4: shallow clone fallback の挙動

**シナリオ UC4-S1: fetch-depth: 0 によって fallback を回避**

```gherkin
Feature: shallow clone 回避
  Scenario: CI 上で fetch-depth: 0 により git describe が tag を引ける
    Given actions/checkout@v4 に fetch-depth: 0 を指定
    When CI で git describe --tags --always を実行
    Then 0.0.0-DEV fallback ではなく tag 値が出力される
```

### 2.3 ビジネスルール

- CI 上の stamp と install.sh stamp は **同じ値**（同 commit、同 git describe）になること。
- 署名なし配布のため、Gatekeeper 回避手順を Release notes で案内する。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- CI 全体時間: 現状 + 5 分以内。

### 3.2 セキュリティ要件

- 本 issue は署名なし配布のため、Gatekeeper 警告 / 公証なしの旨を Release notes に明記。

### 3.3 ユーザビリティ要件

- DL → 展開 → 起動の手順を Release notes に記載。

### 3.4 可用性要件

- macos-latest runner の障害時は `create-release.yaml` 全体が失敗する。本 issue では retry 戦略は対象外。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- `actions/checkout@v4`（`fetch-depth: 0`）
- `actions/upload-release-asset@v1`（または `softprops/action-gh-release`）
- `softprops/action-gh-release` の files で `.app.zip` を指定

### 4.2 データ形式要件

- `.app.zip`（`ditto -c -k --sequesterRsrc --keepParent`）
