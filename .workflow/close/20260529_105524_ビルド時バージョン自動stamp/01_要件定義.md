**プロジェクト名**: Mac Health Keeper / ビルド時バージョン自動 stamp
**作成日**: 2026 年 05 月 29 日
**最終更新**: 2026 年 05 月 29 日

>
> **用語**: [.agents/CONCEPTS.md §用語規約](../../.agents/CONCEPTS.md#用語規約) を参照。

## 1. 概要

### 1.1 システム概要

macOS 常駐型ユーティリティ Mac Health Keeper のビルド成果物 `.app` の `CFBundleVersion` を、ビルド時に git リポジトリ状態（`git describe --tags --always`）から決定的に注入する仕組みを導入する。`CFBundleShortVersionString` は手動 semver の正本のまま維持し、About アラート文言は `Bundle.main.infoDictionary` から動的取得する。

### 1.2 用語集

| 用語 | 説明 |
| --- | --- |
| CFBundleVersion | macOS アプリのビルド識別子。本 issue では git 由来で自動 stamp する対象。 |
| CFBundleShortVersionString | macOS アプリのユーザー向け semver。本 issue では手動 bump 運用を維持。 |
| stamp | `plutil -replace` 等で Info.plist のキーに値を上書きする操作。 |
| 案 Y | 本 issue で採用した方針。「CI が tag、`install.sh` が `git describe` で stamp」する案。 |
| install.sh 経路 | ユーザーがリポジトリ直下で `./install.sh` を実行して `.app` を作る経路。 |
| Makefile 経路 | 開発者が `make build` で `build/MacHealth` バイナリを生成する経路。**現行 Makefile は `.app` バンドルを組み立てないため stamp 対象が無く**、stamp は install.sh 経路のみで実施する（02 §10-4 参照）。 |
| About 動的取得 | Swift コードで `Bundle.main.infoDictionary["CFBundleShortVersionString"]` を読む方式。 |

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 開発者として、Info.plist の二重更新作業を消したい

- **As a** Mac Health Keeper の開発者
- **I want to** `CFBundleVersion` の手動更新を不要にする
- **So that** semver bump 時の追従漏れリスクを構造的に消したい

**受け入れ基準**:
- `src/Info.plist` の `CFBundleVersion` はテンプレ値のままで、commit ごとに変える必要がない。
- semver bump 時、開発者が手動で触るのは `CFBundleShortVersionString` のみ。

#### ストーリー 2: 保守担当として、配布された .app から元 commit を逆引きしたい

- **As a** 保守担当者
- **I want to** 配布された `.app` の `CFBundleVersion` から元 commit を特定したい
- **So that** ユーザー報告のバージョンから即座にコードへ辿れる

**受け入れ基準**:
- `defaults read .../Contents/Info CFBundleVersion` 出力が `git describe --tags --always` の出力と一致し、git 履歴から逆引きできる。

#### ストーリー 3: エンドユーザーとして、About 表示の semver が常に最新を指していてほしい

- **As a** Mac Health Keeper のエンドユーザー
- **I want to** About アラートのバージョン表記が最新版を反映していること
- **So that** 自分の使用バージョンを正しく把握できる

**受け入れ基準**:
- About アラートの `バージョン X.Y` 表記が、Info.plist の `CFBundleShortVersionString` と必ず一致する（ハードコードによる乖離が起きない）。

#### ストーリー 4: AI / 規約担当として、正本ルールに「役割分離」を明記したい

- **As a** 規約整備担当
- **I want to** `CFBundleVersion` と `CFBundleShortVersionString` の役割分離をルール文書に書き込みたい
- **So that** 後続の AI セッション / 人間が誤って `CFBundleVersion` を手動 bump しないように構造的にガードできる

**受け入れ基準**:
- `.agents/spec/04_仕様更新ルール.md` に「`CFBundleVersion` は git 由来で自動 stamp / `CFBundleShortVersionString` は手動 semver」が明文化されている。

### 2.2 BDD ユースケース

#### ユースケース 1: install.sh による CFBundleVersion stamp

ビルド直前に `install.sh` が `git describe --tags --always` を取得し、staged `Info.plist` に `plutil -replace CFBundleVersion -string <derived>` で注入する。

**シナリオ 1: 同 commit からの 2 回 install で同値**

> 前提: 2 回の install の間に作業ツリーへの変更を行わない（dirty 化させない）。本 issue では `git describe` に `--dirty` を**付けない**ため、未コミット変更が無い限り 2 回の出力は等価。

```gherkin
Feature: install.sh による CFBundleVersion 注入
  Scenario: 同 commit から 2 回 install しても CFBundleVersion が一致する
    Given 作業ツリーが commit C にチェックアウトされている
    And  リポジトリに tag が存在しないか、存在しても影響なし
    And  2 回の install の間に作業ツリーへの変更を一切行わない
    When  ./install.sh を 2 回連続で実行する
    Then  両方の生成 .app の `defaults read .../Contents/Info CFBundleVersion` 出力が同値である
    And   その値は `git describe --tags --always` の出力と一致する
```

#### ユースケース 2: tag が存在する commit からの stamp

`git describe --tags` が tag 名を返すケース。CI が main マージ時に tag を打った直後の挙動。

**シナリオ 1: tag 直上の commit**

```gherkin
Feature: tag 由来の CFBundleVersion
  Scenario: tag が打たれた commit から install すると CFBundleVersion が tag 名になる
    Given commit C に tag T（例: v20260530.123045 もしくは v1.3.0）が存在する
    And  作業ツリーが commit C にチェックアウトされている
    When  ./install.sh を実行する
    Then  生成 .app の CFBundleVersion が T と一致する
```

#### ユースケース 3: tag 未存在 commit からの stamp（fallback）

開発中 commit や、CI が tag を打つ前の状態。

**シナリオ 1: 短縮 SHA fallback**

```gherkin
Feature: tag が無い場合の fallback
  Scenario: tag 不在 commit から install すると short SHA fallback が入る
    Given リポジトリに到達可能な tag が一切存在しない
    And  作業ツリーが commit C にチェックアウトされている
    When  ./install.sh を実行する
    Then  生成 .app の CFBundleVersion が `git describe --always`（短縮 SHA）の出力と一致する
    And   CFBundleVersion が空文字列ではない
```

#### ユースケース 4: About 表示の動的取得

Swift コードで Info.plist から動的に読む。

**シナリオ 1: semver bump 時に About が自動追従**

```gherkin
Feature: About 表示の動的取得
  Scenario: CFBundleShortVersionString を手動 bump すれば About アラートが追従する
    Given Info.plist の CFBundleShortVersionString を X.Y から X.Y+1 に変更した
    And  Swift コードの showAbout の文言にバージョンリテラルは存在しない
    When  ./install.sh で再ビルドして About を開く
    Then  About アラートに「バージョン X.Y+1」と表示される
```

**シナリオ 2: Bundle 情報取得失敗時の fallback**

> 検証方法の補足: `Bundle.main.infoDictionary` 自体は Bundle 副作用に依存するため XCTest / MacHealthCheck では直接スタブできない。本 issue では純粋関数 `formatAboutVersionLine(_:)` の `nil` / 空文字入力経路をテストすることで fallback ロジックを網羅し、`Bundle.main.infoDictionary` の nil 挙動はランタイム手動確認（受け入れ基準）に倒す。02 §6.1 / 03 §2.5.3 と整合。

```gherkin
Feature: About 表示の動的取得（fallback）
  Scenario: Bundle.main.infoDictionary が空でも About がクラッシュしない
    Given Bundle.main.infoDictionary["CFBundleShortVersionString"] が nil を返す状況を仮定する
    When  showAbout が呼び出される（純粋関数経路では formatAboutVersionLine(nil) を呼ぶ）
    Then  About アラートが既定の fallback 文字列「バージョン 不明」でフォールバック表示される
    And   アプリがクラッシュしない
```

#### ユースケース 5: CI による自動 tag と Release

main マージ時に自動 tag → Release が成立する。

> 実態との整合: 既存 `.github/workflows/create-release.yaml` は **`ubuntu-latest`** runner で `git tag` / `git push` / `gh release create --generate-notes` のみを実行する軽量ワークフロー。`plutil` を用いた stamp は CI では実行せず、stamp は install.sh 経路（macOS ローカル）で行う。

**シナリオ 1: main マージで自動 tag**

```gherkin
Feature: CI 自動 tag 付与
  Scenario: main へのマージで CI が tag を打ち Release を作成する
    Given feature ブランチが main へマージされた
    When  GitHub Actions の create-release.yaml ワークフローが起動する
    Then  新しい tag（既存規約: `v$(TZ=Asia/Tokyo date +%Y%m%d.%H%M%S)` 日時タグ）がリポジトリに push される
    And   その tag に対応する GitHub Release が公開される
```

#### ユースケース 6: 既存正本ルールとの整合

`.agents/spec/04_仕様更新ルール.md` の役割分離との整合確認。

**シナリオ 1: 正本ルールが矛盾しない**

```gherkin
Feature: 正本ルール整合
  Scenario: 04_仕様更新ルール の役割分離追記後、既存正本ルールと矛盾しない
    Given .agents/spec/04_仕様更新ルール.md が更新済み
    When  「CFBundleVersion = git 由来」「CFBundleShortVersionString = 手動 semver」を明記する
    Then  「アプリバージョンの正本は src/Info.plist」とする既存記述と矛盾しない（正本=Info.plist という前提は保たれる）
    And   「バージョン更新時の必須手順」の手順 2（showAbout の追従更新）は「動的取得化により不要」と明示される
```

### 2.3 ビジネスルール

- `CFBundleVersion` は git 履歴から決定可能な値のみを格納する（任意手入力を受け付けない）。
- `CFBundleShortVersionString` は人間がリリース判断で bump する semver である（自動化対象外）。
- About 表示は `CFBundleShortVersionString` を一次情報とし、Swift コードにバージョン値をハードコードしない。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- install.sh 実行時の追加コストは `git describe` 1 回 + `plutil` 1 回（合計 < 1 秒目安）。

### 3.2 セキュリティ要件

- 注入文字列は `git` 出力のみ。任意ユーザー入力を経由させない。
- `plutil -replace` の対象は staged の Info.plist（`$APP_DIR/Contents/Info.plist` または build ステージング配下）に限定し、`src/Info.plist` のリポジトリ実体は書き換えない。

### 3.3 ユーザビリティ要件

- エンドユーザーは About アラートで semver を確認できる。動的取得失敗時も fallback でクラッシュしない。

### 3.4 可用性要件

- tag 未存在の commit でもビルドが失敗しない（`git describe --always` の fallback）。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- 外部 API なし。GitHub Actions の `create-release.yaml` ワークフロー（YAML 契約）に対しては、本 issue では **A 案（流用）採用時は変更なし**。B 案（semver タグ切替）を採る場合のみ契約変更となり、その場合は `.agents/spec/05_契約変更ルール.md` の該当範囲（CHANGELOG / ルール文書反映）に従う。

### 4.2 データ形式要件

- `CFBundleVersion` の値は文字列。`git describe --tags --always` 出力に一致する。

---

## 5. 制約事項

- macOS 標準 `plutil` 前提。**stamp は install.sh 経路（macOS ローカル / エンドユーザー端末）でのみ実行**する。`check.yml`（`make check`）は `macos-latest` runner を維持、`create-release.yaml` は既存どおり `ubuntu-latest` runner（tag/Release 発行のみで stamp は行わない）。
- 既存 `make check` がグリーンであること。
- 既存 `feature/20260529`（PR #3）と本 issue の競合は別途マージ順序で解消する。
- `git describe --tags` 出力に `--dirty` マーカは含めない（決定性確保のため、作業ツリー dirty 判定はスコープ外）。
- CI（`create-release.yaml`）は本 issue 範囲では既存ワークフローを変更しないため、`actions/checkout` の `fetch-depth` も既存値（既定 = `1`）のままで影響なし（CI 上で `git describe` を呼ばないため）。ローカル install.sh 経路では通常の clone（全 tag 取得）を前提する。
