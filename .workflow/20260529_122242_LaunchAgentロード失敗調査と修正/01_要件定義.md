# 要件定義書: LaunchAgent monitor/docker/refresh ロード失敗の調査と修正

**プロジェクト名**: Mac Health Keeper / LaunchAgent ロード失敗の調査と修正
**作成日**: 2026 年 05 月 29 日
**最終更新**: 2026 年 05 月 29 日

---

## 1. 概要

### 1.1 システム概要

`install.sh` が `~/Library/LaunchAgents/` 配下に 4 件の plist（uptime / monitor / docker / refresh）を配置・ロードする。現状は 3 件が load 失敗となっている。本 issue では「実機での load 成功」と「期待タイミング実行」を BDD 化する。

### 1.2 用語集

| 用語 | 説明 |
|------|------|
| LaunchAgent | macOS の launchd によりユーザーセッションで常駐するサービス |
| bootstrap | `launchctl bootstrap gui/<uid> <plist>` によるサービス登録 |
| bootout | `launchctl bootout gui/<uid>/<label>` によるサービス登録解除 |
| StartCalendarInterval | plist で指定する時刻ベースのスケジュール |
| StartInterval | plist で指定する秒数間隔のスケジュール |
| RunAtLoad | plist で load 時に即実行するフラグ |

---

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: install 体験の正常化

- **As a** Mac Health Keeper のエンドユーザー（macOS 開発者）
- **I want to** `./install.sh` の出力に「⚠ ロード失敗」が一切表示されない状態を見たい
- **So that** 新規不具合の混入をノイズで隠さず検知できるようにしたい

**受け入れ基準**:

- install 出力の「⚠ ロード失敗」表記が 0 件
- 4 LaunchAgent すべてが `launchctl print gui/$(id -u)/<label>` で確認可能

#### ストーリー 2: 常駐機能の動作保証

- **As a** Mac Health Keeper のエンドユーザー
- **I want to** monitor / docker / refresh が期待タイミングで実行されることを実機で確認したい
- **So that** メニューバーの数値が最新で、常駐機構が正しく機能していることを信頼できる

**受け入れ基準**:

- monitor / docker / refresh の各 plist のスケジュールに従い実行された痕跡（ログ / `last exit code` / 状態変化）が観測できる

### 2.2 BDD ユースケース

#### UC1: LaunchAgent 4 件の load 成功

**シナリオ UC1-S1: 新規 install での 4 件 load 成功**

```gherkin
Feature: LaunchAgent ロード
  Scenario: 新規 install で 4 LaunchAgent すべてが load 成功する
    Given ~/Library/LaunchAgents/ に MacHealth 関連 plist が存在しない
    When ./install.sh を実行する
    Then 標準出力に「⚠ ロード失敗」が 0 件
    And `launchctl print gui/$(id -u)/com.github.adachi-tatsuru.machealth.uptime` が `state` を返す
    And `launchctl print gui/$(id -u)/com.github.adachi-tatsuru.machealth.monitor` が `state` を返す
    And `launchctl print gui/$(id -u)/com.github.adachi-tatsuru.machealth.docker` が `state` を返す
    And `launchctl print gui/$(id -u)/com.github.adachi-tatsuru.machealth.refresh` が `state` を返す
```

**シナリオ UC1-S2: 既存ロード状態からの再 install**

```gherkin
Feature: LaunchAgent ロード
  Scenario: 既存 LaunchAgent がロード済みの状態で再 install しても 4 件すべて load 成功する
    Given ~/Library/LaunchAgents/ に旧 plist が存在し、launchctl にもロード済み
    When ./install.sh を再実行する
    Then 旧 plist の bootout が成功し、新 plist の bootstrap が 4 件すべて成功する
    And install 出力の「⚠ ロード失敗」表記が 0 件
```

#### UC2: 期待タイミング実行

**シナリオ UC2-S1: monitor の期待実行**

```gherkin
Feature: LaunchAgent 期待タイミング実行
  Scenario: monitor が plist の StartInterval に従い実行される
    Given monitor LaunchAgent が load 成功している
    When plist の StartInterval / StartCalendarInterval / RunAtLoad に従う時間が経過する
    Then `launchctl print gui/$(id -u)/com.github.adachi-tatsuru.machealth.monitor` の `last exit code` または `runs` が更新される
    And `~/.local/share/mac-health/logs/monitor.log`（または同等パス）に実行痕跡が追加される
```

**シナリオ UC2-S2: docker の期待実行**

```gherkin
Feature: LaunchAgent 期待タイミング実行
  Scenario: docker が plist のスケジュールに従い実行される
    Given docker LaunchAgent が load 成功している
    When plist のスケジュールに従う時間が経過する
    Then docker 監視結果のログまたはメトリクスファイルが更新される
```

**シナリオ UC2-S3: refresh の期待実行**

```gherkin
Feature: LaunchAgent 期待タイミング実行
  Scenario: refresh が plist のスケジュールに従い実行される
    Given refresh LaunchAgent が load 成功している
    When plist のスケジュールに従う時間が経過する
    Then refresh の実行ログまたは UI 側の更新時刻が新しくなる
```

#### UC3: smoke test での回帰検知

**シナリオ UC3-S1: 4 LaunchAgent load 検証スモークテスト**

```gherkin
Feature: LaunchAgent 回帰検知
  Scenario: scripts/test/launchagent_load_smoke_test.sh が install 直後の 4 件 load 成功を検証する
    Given ./install.sh を完了した直後の状態
    When bash scripts/test/launchagent_load_smoke_test.sh を実行する
    Then 4 件すべての label に対する `launchctl print` が `could not find service` ではない
    And EXIT=0 が返る
```

### 2.3 ビジネスルール

- LaunchAgent の load 失敗は **install フェーズの不合格**とみなす（warn ではなく fail）。
- plist 構文エラーは CI で `plutil -lint` により事前検知する。
- 期待タイミング実行は **実機検証必須**（CI ランナーに GUI セッションがないため）。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- install 全体の所要時間増加は 5 秒以内。

### 3.2 セキュリティ要件

- plist の `ProgramArguments` パスは `~/.local/bin/mac-health/` 配下に限定。

### 3.3 ユーザビリティ要件

- install 出力の警告ノイズを 0 にする。

### 3.4 可用性要件

- 既存ロード状態 → 再 install のパスでも load 成功を保証。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- `launchctl bootstrap gui/<uid> <plist>` / `launchctl bootout gui/<uid>/<label>` / `launchctl print gui/<uid>/<label>`。

### 4.2 データ形式要件

- plist は XML 形式（Apple plist DTD）。`plutil -lint` で構文検証。

---

## 5. 制約事項

- 本 issue ではドキュメント（00〜03）のみ作成し、実装は行わない。
- 期待タイミング実行の検証は **macOS 実機**でのみ可能。CI 上では構文検証に留める。
