# 要件定義書: Makefile build ターゲットで .app バンドルを生成する拡張

**プロジェクト名**: Mac Health Keeper / Makefile build .app 拡張
**作成日**: 2026 年 05 月 29 日
**最終更新**: 2026 年 05 月 29 日

---

## 1. 概要

### 1.1 システム概要

`make build` が現状 `build/MacHealth` 単体バイナリのみを生成しているのを `.app` バンドル化に拡張し、`scripts/lib/version_stamp.sh` を Makefile 経路で再利用可能にする。

### 1.2 用語集

| 用語 | 説明 |
|------|------|
| .app バンドル | macOS の Application bundle 形式（ディレクトリ構造）。`Contents/MacOS/<executable>` と `Contents/Info.plist` を含む |
| CFBundleVersion | Info.plist 内のビルド識別子。本プロジェクトでは git describe 出力で stamp |
| CFBundleShortVersionString | ユーザー向け semver。手動 bump を維持 |
| version_stamp.sh | `scripts/lib/version_stamp.sh`。`git describe` 出力で `CFBundleVersion` を `plutil -replace` 注入 |

---

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: 開発者が install せずに .app を確認したい

- **As a** 開発者
- **I want to** `make build` だけで `build/MacHealth.app` を組み立て、`CFBundleVersion` を確認したい
- **So that** install.sh の副作用（LaunchAgent ロード、ログイン項目登録）を避けたい

**受け入れ基準**:

- `build/MacHealth.app/Contents/MacOS/MacHealth` と `Contents/Info.plist` が存在
- `defaults read build/MacHealth.app/Contents/Info CFBundleVersion` が `git describe --tags --always` と一致

#### ストーリー 2: CI で .app artifact を組み立てたい

- **As a** CI / GitHub Actions
- **I want to** `make build` で `.app` を組み立て、artifact として配布したい
- **So that** Issue C（B 案: CI stamp）の前提を満たしたい

**受け入れ基準**:

- `make build` がエラーなく完了
- `.app` が CI artifact としてアップロード可能なディレクトリ構造

### 2.2 BDD ユースケース

#### UC1: .app バンドル生成

**シナリオ UC1-S1: 通常 commit からの .app 生成**

```gherkin
Feature: make build .app 生成
  Scenario: 通常 commit から make build で .app が生成される
    Given クリーンな build/ ディレクトリ
    When make build を実行する
    Then build/MacHealth.app/Contents/MacOS/MacHealth が実行可能ファイルとして存在する
    And build/MacHealth.app/Contents/Info.plist が存在する
    And defaults read build/MacHealth.app/Contents/Info CFBundleVersion が `git describe --tags --always` と一致する
```

**シナリオ UC1-S2: tag 無し commit の fallback**

```gherkin
Feature: make build .app 生成
  Scenario: tag が存在しない commit から make build を実行すると fallback 値が入る
    Given tag が存在しない HEAD
    When make build を実行する
    Then CFBundleVersion が `git describe --always` の出力（短縮 SHA）と一致する
```

#### UC2: stamp の決定性

**シナリオ UC2-S1: 同一 commit から 2 回 make build しても CFBundleVersion が一致**

```gherkin
Feature: stamp 決定性
  Scenario: 同一 commit から 2 回 make build しても CFBundleVersion が一致する
    Given 作業ツリーに変更がない
    When make build を 2 回連続実行する
    Then 2 回の CFBundleVersion が同一である
```

#### UC3: install.sh との非干渉

**シナリオ UC3-S1: make build が install.sh の状態に影響しない**

```gherkin
Feature: make build と install.sh の非干渉
  Scenario: make build が LaunchAgent ロード状態 / ~/Applications/MacHealth.app に影響しない
    Given install.sh 後の状態
    When make build のみを実行する
    Then ~/Applications/MacHealth.app の mtime が変化しない
    And launchctl print の出力が変化しない
```

### 2.3 ビジネスルール

- `make build` は `install.sh` の責務を侵害しない（LaunchAgent ロード・ログイン項目登録は対象外）。
- `CFBundleVersion` の stamp 値は `version_stamp.sh` の既存挙動を踏襲する（重複実装しない）。

---

## 3. 非機能要件

### 3.1 パフォーマンス要件

- 既存 `make build` 比 +1 秒以内。

### 3.2 セキュリティ要件

- 外部入力なし。

### 3.3 ユーザビリティ要件

- `make build` の出力に「`build/MacHealth.app` を生成」「stamp 完了: `<value>`」が表示される。

### 3.4 可用性要件

- shallow clone 環境では fallback `0.0.0-DEV` を許容（Issue D で README 注意書き対応）。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- `plutil -replace CFBundleVersion -string "<derived>" <Info.plist>`
- `git describe --tags --always`

### 4.2 データ形式要件

- `Info.plist` は XML 形式。

---

## 5. 制約事項

- macOS 専用（`plutil` 依存）。Linux CI では実行不可。
- `make build` から LaunchAgent ロードや ~/Applications/ 配置は行わない。
