## 1. 概要

### 1.1 システム概要

Mac Health Keeper の純粋ロジック（日時計算・相対表示・通知クールダウン・閾値判定）を単体テストで保護し、Swift とシェルのテスト/ビルドを単一手順で実行できる足場を整える。

### 1.2 用語集

| 用語 | 説明 |
| ---- | ---- |
| 純粋ロジック | 外部コマンド・I/O に依存せず入力から出力が決まる関数 |
| クールダウン | 同一キーの通知を一定時間抑制する仕組み（`should_notify`） |
| bats | Bash Automated Testing System。シェルの単体テスト |

---

## 2. 機能要件

### 2.1 ユーザーストーリー

#### ストーリー 1: Swift 純粋ロジックの保護

- **As a** Mac Health Keeper の開発者
- **I want to** `nextDailyRun`/`relativeTimeShort`/`relativeNext` の単体テストを持つ
- **So that** リファクタ時に時刻計算・表示のリグレッションを検知できる

**受け入れ基準**:

- 上記 3 関数に対し正常系・境界系のテストが存在する。
- `swift test` 等の単一コマンドで実行・通過する。

#### ストーリー 2: シェル純粋ロジックの保護

- **As a** 開発者
- **I want to** `should_notify` とメトリクス閾値判定の bats テストを持つ
- **So that** 通知抑制・閾値超過の判定が壊れていないことを保証できる

**受け入れ基準**:

- クールダウン未経過/経過の双方で `should_notify` の戻り値を検証する。
- swap/compressed/load/pressure の各閾値で「超過→通知対象」「未満→非通知」を検証する。

### 2.2 BDD ユースケース

#### ユースケース 1: 翌日実行時刻の算出

`nextDailyRun(hour:minute:)` は現在時刻を過ぎていれば翌日の同時刻を返す。

**シナリオ 1: 指定時刻が現在より後**

```gherkin
Feature: 翌日実行時刻の算出
  Scenario: 指定時刻が現在より後なら当日のその時刻を返す
    Given 現在が当日 08:00 で hour=9 minute=0 を指定する
    When nextDailyRun(hour:9, minute:0) を呼ぶ
    Then 当日 09:00 を表す Date が返る
```

**シナリオ 2: 指定時刻が現在より前**

```gherkin
Feature: 翌日実行時刻の算出
  Scenario: 指定時刻が現在より前なら翌日のその時刻を返す
    Given 現在が当日 10:00 で hour=9 minute=0 を指定する
    When nextDailyRun(hour:9, minute:0) を呼ぶ
    Then 翌日 09:00 を表す Date が返る
```

#### ユースケース 2: 相対時刻表示

`relativeTimeShort`/`relativeNext` は経過/残り時間を短い文字列に整形する。

**シナリオ 1: 直近の過去時刻**

```gherkin
Feature: 相対時刻表示
  Scenario: 数分前の時刻を短い相対表現にする
    Given 現在から 3 分前の Date を渡す
    When relativeTimeShort(date) を呼ぶ
    Then 「分」を含む短い相対文字列が返る
```

**シナリオ 2: 次回実行までの残り**

```gherkin
Feature: 相対時刻表示
  Scenario: interval 指定で次回までの残りを表現する
    Given 直近実行時刻と intervalSec=300 を渡す
    When relativeNext(date, intervalSec:300) を呼ぶ
    Then 次回実行までの残りを表す文字列が返る
```

#### ユースケース 3: 通知クールダウン判定

`should_notify` は前回通知からクールダウン未経過なら抑制する。

**シナリオ 1: クールダウン未経過**

```gherkin
Feature: 通知クールダウン判定
  Scenario: 前回通知から cooldown 未経過なら通知しない
    Given COOLDOWN_FILE に key の last=現在直近 が記録されている
    When should_notify "swap" を呼ぶ
    Then 戻り値が 1（非通知）になる
```

**シナリオ 2: クールダウン経過**

```gherkin
Feature: 通知クールダウン判定
  Scenario: 前回通知から cooldown 経過なら通知し記録を更新する
    Given COOLDOWN_FILE に key の last=十分過去 が記録されている
    When should_notify "swap" を呼ぶ
    Then 戻り値が 0（通知）になり COOLDOWN_FILE が更新される
```

#### ユースケース 4: メトリクス閾値判定

monitor.sh は各メトリクスが閾値以上なら通知対象とする。

**シナリオ 1: スワップ閾値超過**

```gherkin
Feature: メトリクス閾値判定
  Scenario: swap_used_mb が閾値以上なら通知対象
    Given swap_used_mb >= THRESHOLD_SWAP_USED_MB
    When 判定ロジックを評価する
    Then スワップ通知の分岐が真になる
```

**シナリオ 2: スワップ閾値未満は非通知**

```gherkin
Feature: メトリクス閾値判定
  Scenario: swap_used_mb が閾値未満なら通知対象にならない
    Given swap_used_mb < THRESHOLD_SWAP_USED_MB
    When 判定ロジックを評価する
    Then スワップ通知の分岐が偽になる
```

**シナリオ 3: 圧縮メモリ閾値超過**

```gherkin
Feature: メトリクス閾値判定
  Scenario: compressed_gb が閾値以上なら通知対象
    Given compressed_gb >= THRESHOLD_COMPRESSED_GB
    When 判定ロジックを評価する
    Then 圧縮メモリ通知の分岐が真になる
```

**シナリオ 4: Load Average 閾値超過**

```gherkin
Feature: メトリクス閾値判定
  Scenario: load_avg が load_threshold（ncpu × THRESHOLD_LOAD_AVG_MULTIPLIER）以上なら通知対象
    Given load_avg >= ncpu * THRESHOLD_LOAD_AVG_MULTIPLIER
    When 判定ロジックを評価する
    Then load 通知の分岐が真になる
```

**シナリオ 5: メモリプレッシャー critical**

```gherkin
Feature: メトリクス閾値判定
  Scenario: free_pct が 10 未満なら pressure=critical
    Given free_pct=5
    When pressure 判定を評価する
    Then mem_pressure が "critical" になる
```

**シナリオ 6: メモリプレッシャー normal（非通知）**

```gherkin
Feature: メトリクス閾値判定
  Scenario: free_pct が 25 以上なら pressure=normal で非通知
    Given free_pct=50
    When pressure 判定を評価する
    Then mem_pressure が "critical" ではなく pressure 通知の分岐が偽になる
```

### 2.3 ビジネスルール

- テストは `.agents/TEST_BDD_FORMAT.md` に従い、ユースケース/シナリオ doc コメントと Given/When/Then インラインコメントを付与する。
- テストは破壊的副作用（実通知・実ファイル削除）を起こさない（一時ディレクトリ・固定入力を使う）。

## 3. 非機能要件

### 3.1 パフォーマンス要件

- 全テストが数十秒以内に完了する。

### 3.2 セキュリティ要件

- テスト内で外部ネットワーク・任意コマンド実行を行わない。

### 3.3 ユーザビリティ要件

- テスト実行手順が docs もしくは README で 1 コマンドとして示される。

### 3.4 可用性要件

- bats 不在環境でも代替手段（自前 assert）でシェルテストが実行できる。

---

## 4. 外部インターフェース要件

### 4.1 API 要件

- 既存関数のシグネチャを変えない（テスト追加が目的）。

### 4.2 データ形式要件

- COOLDOWN_FILE 形式（`key:epoch`）を維持する。

---

## 5. 制約事項

- Swift: XCTest / Swift Package Manager。シェル: bats（代替可）。
- 純粋ロジックは外部コマンド非依存の関数に限定して検証する。
