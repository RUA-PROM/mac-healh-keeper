**配置**: `.agents-project/受け入れ基準ルール.md`
**優先度**: 本ファイルは [`./README.md`](./README.md) の §優先順位 に基づき、`.agents/` 配下の汎用規約より**優先**される。
**正本との関係**: 関連する汎用規約は次を参照する。本ファイルは「Mac Health Keeper プロジェクトの追加要件・上書き要件」のみを定義する。

## 1. なぜこのルールが必要か（背景）

PR #3 マージ直後にユーザー環境で `./install.sh` を実行した結果、`LaunchAgent`（monitor / docker / refresh）の **3 件のロード失敗**が再発見された。当該失敗は [`.workflow/close/20260529_083530_メトリクス非表示修正/04_review.md` §6 軽微指摘・§10.6](../.workflow/close/20260529_083530_メトリクス非表示修正/04_review.md) で既知事象として残置されていたものであり、**「`make check` が緑 = 完了」と判断したことに起因する重大なプロセス欠陥**である。

教訓は次のとおり。

- `make check` は単体テスト・shell テスト・smoke の **静的観点**しか網羅できない。
- LaunchAgent のロード結果・常駐プロセスの起動・メニューバー UI の挙動・`.app` のバージョン表記といった **統合観点**は `make check` で検証できない。
- それらを検証するには **実機（ローカル macOS）で `install.sh` または `make install` を実行し、結果を観測する**しか手段が無い。
- にもかかわらず、直前のサブエージェントは `make check` のみで `04_review` を緑として完了報告した。**結果として既知の不具合がユーザーに渡った**。

本プロジェクトでは、上記の再発を構造的に防ぐため、**受け入れ基準に「ローカル環境での実機 install + 動作確認」を必須化**する。

---

## 2. 受け入れ基準の重要性（再確認）

- **実装完了 ≠ issue 完了**。実装が動くようになった時点では受け入れ基準は満たされていない。
- **受け入れ基準で定義した観点を全て満たした時点で、初めて issue が完了**となる。
- 受け入れ基準は、以下 4 種類の観点を **網羅**するように設計する。
  1. 機能観点（仕様どおりに動くか）
  2. 回帰観点（既存機能を壊していないか）
  3. **統合観点（実環境で導入・常駐・連携が成立するか）** — **本ルールで強制**
  4. ドキュメント観点（仕様書・正本ルールが追従しているか）

`make check` が満たすのは主に 1〜2 と一部の 4。**3 は本ルールでしか担保できない**。

---

## 3. 実装フェーズ完了の必須要件（DoD 上書き）

本プロジェクトでは、`.agents/workflow/PHASES.md` の DoD に **以下 3 件を追加**する。実装フェーズ（`implement-feature`）またはレビューフェーズ（`verify-and-close`）の完了判定で **すべて満たす**こと。

### 3.1 `make check` が緑であること（既存）

- `make check` がローカルおよび CI（`.github/workflows/check.yml`）の両方で緑であること。

### 3.2 ローカル実機で `install.sh` または `make install` を実行し、対象機能が動作することを確認したエビデンスがある（**本ルールで追加**）

- 実機 = ローカル macOS（開発者の端末）。
- 実行コマンド: 原則 `./install.sh`（または `make install` / `make reinstall`）。
- 確認対象は次を **最低限** 含むこと。
  - 終了コード `0`
  - 当該 issue で変更した機能（メニュー表示・LaunchAgent ロード・メトリクス・バージョン stamp 等）が **期待どおりに動作している**こと
  - **副作用として既知の他不具合が混入していないこと**（例: 他 LaunchAgent ロード失敗が新たに発生していないか）

### 3.3 `make check` で検証しきれない統合観点はローカル実機確認必須（**本ルールで追加**）

`make check` で SKIP / 未網羅となる以下は **必ず**ローカル実機で確認する。

- LaunchAgent の **load 結果**（`launchctl bootstrap` または `bootout` のエラー有無）
- LaunchAgent の **期待タイミングでの実行**（`StartCalendarInterval` / `StartInterval` / `RunAtLoad` の発火確認）
- 常駐プロセス（`MacHealth`）の **起動・PID 再生成・mtime 更新**
- メニューバー UI の表示（🩺 アイコン、メニュー項目、About アラート文言）
- `.app` バンドルの `CFBundleVersion` / `CFBundleShortVersionString` の表示

GUI 目視確認のうち CLI から検証不可能な項目は、04_review に **「ユーザー側目視確認の依頼」** として明示列挙して残してよい（ただし、CLI で検証可能な部分は必ずサブが確認してエビデンスを残す）。

### 3.4 エビデンスの記録先

- エビデンスは **04_review.md** または **`memo/` 配下**に、以下の形式で残すこと。
  - 実行したコマンド（コピペ可能な形）
  - 実行ログの要点（**終了コード・所要時間・主要出力**）
  - 検証結果（受け入れ基準ごとに `OK` / `NG` を判定）
  - 残課題（GUI 目視・別 issue 候補 等）

参考実装: [`.workflow/close/20260529_105524_ビルド時バージョン自動stamp/memo/20260529_121145_install-verification.md`](../.workflow/close/20260529_105524_ビルド時バージョン自動stamp/memo/20260529_121145_install-verification.md) は本ルール適用の見本形（事前状態 / install ログ要点 / 事後検証 / GUI 目視 / 残課題）。

## 4. 受け入れ基準への記載必須項目（00_要求定義 強制）

本ルールが適用される issue では、`00_要求定義.md` §6「成功基準」（または該当する受け入れ基準セクション）に **次の文言を明記**すること。

> **基準（実機検証）**: ローカル環境で `./install.sh`（または `make install` / `make reinstall`）を実行し、本 issue で変更・追加した機能が期待どおり動作していることを確認したエビデンス（コマンド出力・確認手順・結果）が `04_review.md` または `memo/` 配下に記録されていること。本基準の根拠は [`.agents-project/受け入れ基準ルール.md`](../../.agents-project/受け入れ基準ルール.md) §3.2–3.4。

文言は趣旨が同じであれば issue 固有の語彙にカスタマイズして構わない（例: 「`.app` の `CFBundleVersion` が `git describe` 出力と一致することを実機で確認」）が、**「ローカル install + 動作確認 + エビデンス記録」の 3 要素は必ず含めること**。

## 5. 適用範囲

| 対象 | 本ルール適用 | 備考 |
|------|--------------|------|
| 実コード（`src/`、`Sources/`、`Package.swift`、`Makefile`、`install.sh`、`uninstall.sh`、`scripts/`、`launchagents/`）に影響する issue | **必須** | 本ルール完全適用 |
| CI / GitHub Actions の変更 | **必須** | Release artifact のローカル DL → 動作確認まで含む |
| LaunchAgent plist / 常駐サービスに影響する issue | **必須**（最厳格） | load 結果・期待タイミング実行の両方を実機確認 |
| `docs/` 配下のシステム仕様書のみの変更 | **任意**（但し §6 の判断記録は必須） | レビュー用ディレクトリ `docs/00_review/` の運用に従う |
| `.agents/` / `.agents-project/` 配下の規約変更のみ | **任意**（但し §6 の判断記録は必須） | 規約変更による副作用が無いことを確認 |
| README.md / その他ドキュメントのみの変更 | **判断**（但し §6 の判断記録は必須） | install 手順を変更する場合は実機検証必須 |

「任意」「判断」と分類した場合でも、**00_要求定義 §6 または §5 除外要件で「本ルール非適用」の根拠を 1 文で示すこと**（例:「本 issue は `.agents-project/` 配下の規約追加のみで、実行系・配置先・install フローへの影響なし」）。

## 6. 再発防止策（verify-and-close 委譲時の追加 DoD）

`verify-and-close` 実施時、サブエージェントは次を **必須**とする。

### 6.1 禁止事項

- **`make check` のみで `04_review` 緑を報告することを禁止**。本ルール適用 issue では `make check` 緑は必要条件であり十分条件ではない。
- `04_review` の「テスト結果」セクションが `make check` の出力のみで構成されていることを禁止。**実機検証セクション**が別に必要。

### 6.2 必須セクション（04_review への追加）

`04_review.md` には次のセクションを **必ず設ける**（章番号は任意）。

- **実機検証ログ**:
  - 実行コマンド（コピペ可能な形）
  - 終了コード・所要時間
  - 副作用（他 LaunchAgent / 既存機能への影響有無）
  - 当該 issue の受け入れ基準ごとの OK/NG 判定
- **GUI 目視確認の依頼**（CLI で検証不能な観点があれば）

### 6.3 サブからの完了報告フォーマット

サブはオーケストレータに次を返す。

- `make check` の結果（緑/赤）
- **実機 install 実行の有無・終了コード・主要観測点**
- 残課題（GUI 目視 / 別 issue 候補）

`make check` のみで完了報告した場合、オーケストレータは差し戻し（再委譲）する。
